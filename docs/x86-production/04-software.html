BCM Software Installation Clone, configure, and deploy BCM on the Lenovo M910q

This page covers the complete software installation and configuration for a production BCM deployment. The automated setup script handles 14 phases of system configuration — from dependency installation through systemd services to a final smoke test.

Prerequisites

Complete the OS installation (page 03) and system packages (page 04) before proceeding. You should have a working Debian 13 (Trixie) system with network access and a non-root user with sudo privileges.

Clone & Install

Clone the BCM repository into /opt/bcm and take ownership so you can run the application without root: 

cd /opt
sudo git clone https://github.com/geek95dg/Alfa156-headunit.git bcm
sudo chown -R $USER:$USER /opt/bcm
cd /opt/bcm

The Setup Script

The primary install method is setup-x86.sh. It handles everything — from installing system packages to configuring systemd services, kiosk mode, WiFi AP, and more: 

sudo bash config/scripts/setup-x86.sh
Run as root

The script must be run with sudo. It modifies systemd units, GRUB configuration, udev rules, and other system-level settings. Review the USER CONFIG section before running.

14 Setup Phases

The script executes the following phases in order. Each phase is idempotent — you can re-run the script safely after making configuration changes.

# Phase What it does
1 Cleanup Removes old BCM services and configuration files from any previous installation
2 System packages Installs all apt dependencies (X11, Chromium, PipeWire, ffmpeg, Python, build tools, etc.)
3 Python venv Creates .venv virtual environment with versioned Python binary fallback (tries python3.12, python3.11, then python3)
4 Vendor assets Downloads Tailwind CSS and Leaflet for offline operation — no CDN dependency in the car
5 Splash videos Generates placeholder splash videos via ffmpeg if none exist in the splash directory
6 Systemd services Installs and enables bcm-headunit, ignition-watcher, splash, and resume service units
7 Kiosk Configures autologin + X11 + xinitrc with touch-screen input mapping for dual displays
8 Power button Configures acpid for suspend on power button press + sets HandlePowerKey=ignore in logind
9 WiFi AP Sets up hostapd + dnsmasq access point — 2.4 GHz channel 6 with Intel 8265, 5 GHz channel 149 with Fenvi AX200
10 LTE modem Auto-detects Huawei E3372 HiLink USB modem and configures DHCP on its network interface
11 GRUB Silences boot output — sets quiet splash, disables Plymouth, hides GRUB menu
12 Permissions Adds user to dialout, video, audio, bluetooth groups + enables Bluetooth auto-power on boot
13 Test Runs a quick Flask smoke test — starts the application briefly to verify it launches without errors
14 Summary Prints a summary of all installed services, configuration paths, and next steps

User Configuration

Before running the setup script, edit the USER CONFIG section at the top of the file to match your hardware: 

nano config/scripts/setup-x86.sh

Display output names

On the M910q with DP-to-HDMI adapters, output names are typically DP-1 and DP-2 rather than HDMI-1 / HDMI-2. Always verify with xrandr before running the script. Incorrect output names will result in a blank kiosk display.

Production Config (bcm_config.yaml)

The main application configuration lives in config/bcm_config.yaml. Key settings for a production deployment: 

system:
  platform: x86
  simulation: false    # CRITICAL: disables demo/fake data
  log_level: INFO      # reduce from DEBUG for production

serial:
  kline:
    port_x86: /dev/ttyUSB_kline    # udev rule for stable naming
    baudrate: 10400
    ecu_address: 1

wifi:
  enabled: false       # systemd manages the AP, not BCM

modules:
  dashboard: true
  obd: true            # real ECU data via K-Line
  parking: true        # HC-SR04 via Arduino
  environment: true    # DS18B20 via Arduino
  audio: true
  input: true          # Arduino Pro Micro SWC + buttons
  camera: true         # 4-ch USB grabber
  power: true
  multimedia: true     # Android Auto + Bluetooth
  location: true       # USB GPS
  network: true        # LTE modem
  weather: true        # OpenWeatherMap API
simulation: false is critical

When simulation is set to true, BCM generates fake sensor data for development and testing. In a production car build, this must be set to false so the system reads real data from the K-Line ECU, Arduino sensors, and GPS. Leaving simulation enabled in production will mask real vehicle data and hide hardware faults.

USB Device Naming (udev Rules)

USB device paths like /dev/ttyUSB0 can change between reboots depending on enumeration order. Create stable /dev/ symlinks using udev rules so BCM always finds the correct device: 

sudo tee /etc/udev/rules.d/99-bcm-usb.rules >/dev/null <<'EOF'
# K-Line adapter (CP2102)
SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", SYMLINK+="ttyUSB_kline"
# GPS (u-blox)
SUBSYSTEM=="tty", ATTRS{idVendor}=="1546", ATTRS{idProduct}=="01a7", SYMLINK+="ttyUSB_gps"
# Arduino Pro Micro (input)
SUBSYSTEM=="tty", ATTRS{idVendor}=="2341", ATTRS{idProduct}=="8037", SYMLINK+="ttyACM_input"
# Arduino Nano (output)
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", SYMLINK+="ttyUSB_output"
EOF
sudo udevadm control --reload-rules
sudo udevadm trigger
Finding vendor and product IDs

Plug in each USB device one at a time and run lsusb to find its idVendor and idProduct. If you have two devices with the same chipset (e.g., two CP2102 adapters), add ATTRS{serial}=="..." to distinguish them. Find the serial with udevadm info -a /dev/ttyUSB0 | grep serial.

Manual Test

Before relying on systemd auto-start, verify the application runs correctly from the command line: 

source /opt/bcm/.venv/bin/activate
python3 main.py --platform x86 --config config/bcm_config.yaml --frontend
# Open browser: http://localhost:5002
# Ctrl+C to stop
What to verify

Check that the Flask server starts on port 5002, the dashboard loads in a browser, and there are no import errors or missing dependencies in the terminal output. If serial devices are not connected, those modules will log warnings but the application should still start.

Vendor Assets (Offline Operation)

The car has no guaranteed internet connection. All frontend dependencies must be available locally. The vendor asset script downloads Tailwind CSS and Leaflet (for map tiles) into the project’s static assets directory: 

bash config/scripts/download-vendor-assets.sh
Run this while you have internet

This script requires an active internet connection to download assets. Run it during initial setup — not in the car. The setup script (phase 4) calls this automatically, but you can re-run it manually if assets are missing or need updating.
