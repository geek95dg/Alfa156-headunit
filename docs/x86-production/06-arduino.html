Arduino Firmware & Serial Protocol Input controller (Pro Micro) and output controller (Nano) for vehicle I/O

Overview

The x86 M910q has no GPIO header, so all vehicle I/O passes through two USB Arduinos connected via the powered USB hub:

Arduino MCU Role Baud Rate USB Mode
#1 — Pro Micro ATmega32U4 Input — buttons, sensors, vehicle signals 115200 HID + Serial (native USB)
#2 — Nano ATmega328P Output — relays, locks, lights, horn 9600 Serial only (CH340 USB-UART)
Dual USB

The Pro Micro (ATmega32U4) exposes both a HID keyboard device and a CDC serial port over a single USB connection. Button presses are sent as USB HID keycodes (handled by evdev / arduino_hid.py), while sensor data and vehicle signals are sent as plain-text serial messages (handled by arduino_serial.py). Both streams arrive on the same /dev/ttyACM0 port.

SWC Button Mapping (24 Buttons)

Each SWC pod provides 12 buttons via a resistor-ladder circuit. The white wire from each SWC decoder box connects to an analog pin; black to GND and red to 12 V ACC. The firmware reads the ADC value, matches it against calibrated thresholds (tolerance ±40), and sends the corresponding HID keycode.

Pod 2 (indices 12–23) sends identical keycodes to Pod 1. ADC values above 1000 are treated as idle (no button pressed).

SWC Calibration

Default ADC thresholds may not match your specific SWC decoder boxes. The firmware includes an EEPROM-backed calibration routine:

  1. Hold HOME + BACK while powering on the Arduino
  2. Open serial monitor at 115200 baud
  3. Press each button when prompted — Pod 1 first (12 buttons), then Pod 2 (12 buttons)
  4. Calibrated ADC values are saved to EEPROM (magic byte 0xBD at address 0)
  5. Values persist across power cycles; re-calibrate by repeating the process
Collision warning

After calibration, the firmware checks for buttons with ADC values closer than ±40 counts and prints a warning. If two buttons collide, adjust the resistor values in the SWC decoder pod.

Flashing the Pro Micro

  1. Open arduino/rotary_encoder/rotary_encoder.ino in Arduino IDE
  2. Install the HID-Project library via Library Manager
  3. Select board: Arduino Leonardo (ATmega32U4 boards share this profile)
  4. Select port: /dev/ttyACM0
  5. Upload — the Pro Micro resets automatically via USB
Why Arduino Leonardo?

The Pro Micro uses the same ATmega32U4 as the Leonardo. Arduino IDE does not list "Pro Micro" by default — select Arduino Leonardo and it will flash correctly. If using SparkFun boards, install the SparkFun AVR boards package and select SparkFun Pro Micro (5V, 16MHz).

Arduino #2 — Nano Output Controller

Hardware

  • MCU: ATmega328P (CH340 USB-UART bridge)
  • USB: Serial only at 9600 baud
  • Port: /dev/ttyUSB0 (or ttyUSB1)
  • Power domain: Domain A — always on. Vin from the 12 V SLA battery buffer via a 12 V→5 V buck. USB to M910q is used only for the backlight commands when the BCM is awake.
  • Sketch: arduino/output_controller/output_controller.ino
  • Libraries: ArduinoJson (v7), RCSwitch, SoftwareSerial (bundled)
  • Relay module: 10-channel, active-low, opto-isolated (9 of 10 channels used)

Dropped features — OEM systems left untouched

Earlier revisions of this page documented the Nano as a replacement for the OEM central lock, with lock / unlock / RF keyfob learning, headlights, horn, wipers, and blinkers. That concept has been abandoned. The original Alfa 156 systems stay in place. The Nano now focuses on the small set of features the OEM does not provide: 4-window remote control (hold-to-move from a secondary keyfob), BLE-proximity-gated trunk release, and the display backlight PWM.

If you ever want the dropped outputs back (headlights, horn, wipers, blinkers), they need a separate Nano on Domain B with its own sketch — the always-on Nano's pin budget is fully used by the new scope.

Window-remote learning

8 RF codes (one per window-and-direction slot) are stored in EEPROM. Walk through the learning procedure in docs/ARDUINO_SETUP_GUIDE.md § 6.5. In short: send {"cmd":"learn_window","slot":"FL_DOWN"}, press the corresponding remote button, the Nano echoes {"event":"learned","slot":"FL_DOWN","code":1234567}, repeat for the other 7 slots. Slots: FL_UP / FL_DOWN / FR_UP / FR_DOWN / RL_UP / RL_DOWN / RR_UP / RR_DOWN.

BLE proximity gate

The HM-10 BLE module is in central/scanner mode. When the trunk button is pressed, the Nano issues AT+DISC?, scans for 2.5 s, looks for the previously-learned BLE MAC and confirms RSSI is at or above the threshold (default −80 dBm, ~5 m line-of-sight with an iTag). Only then does it pulse the trunk relay. Pair the tag with {"cmd":"learn_ble"} (picks the strongest device in range) or set the MAC explicitly with {"cmd":"set_ble_mac","mac":"AA1122334455"}. Tune sensitivity with {"cmd":"set_ble_rssi","threshold":-75}.

Why D9/D10 are the backlight outputs

On x86 the M910q has no GPIO header, so the display backlight PWM must come from one of the USB Arduinos. The Nano's hardware PWM channels are on D3/D5/D6/D9/D10/D11 — D9 and D10 sit on Timer1 which doesn't conflict with millis(), making them the cleanest choice. The right blinker and wipers (which don't need PWM) move to A0/A1.

JSON Command Protocol

The BCM sends JSON commands over USB serial to the Nano at 9600 baud. Each command is a single JSON object terminated by a newline character. The Nano works autonomously for windows and trunk — the BCM only needs to issue backlight and the configuration commands below; everything else is event-driven from the Nano.

Command JSON Example Behaviour
Backlight {"cmd":"backlight","display":"large","brightness":80} PWM duty on D9 (large/7") or D10 (small/4.3"); accepts "both" too
Health-check {"cmd":"ping"} Reply: {"event":"pong"}
Status dump {"cmd":"status"} Returns active window slot, BLE MAC presence, RSSI threshold, all 8 learned RF codes
Learn window code {"cmd":"learn_window","slot":"FL_DOWN"} Arm 30 s capture for the named slot. Next received RF code is stored.
Learn BLE tag {"cmd":"learn_ble"} 5 s HM-10 scan; stores strongest-RSSI MAC as the known tag
Set BLE MAC {"cmd":"set_ble_mac","mac":"AA1122334455"} Explicit set (12 hex chars). Persisted to EEPROM.
Set BLE threshold {"cmd":"set_ble_rssi","threshold":-75} Trunk-arm RSSI threshold in dBm. Default −80.
Factory reset {"cmd":"clear"} Wipes EEPROM: forgets all 8 RF codes and the BLE MAC

Serial Protocol — Input Messages

The Pro Micro sends plain-text serial messages to the BCM over /dev/ttyACM0 at 115200 baud. The Python module src/input/arduino_serial.py (ArduinoSerialListener class) parses each line and publishes it to the event bus. Auto-detection tries /dev/ttyACM0..1, /dev/ttyUSB0..2, and falls back to stub mode if no port is found.

Message Example Event Bus Topic Value Type
DOOR:keys DOOR:FL=1,FR=0,RL=0,RR=0,BONNET=0,TRUNK=0 vehicle.doors dict {fl, fr, rl, rr, bonnet, trunk} → bool
HBRAKE:X HBRAKE:1 vehicle.handbrake bool
IGN:X IGN:1 vehicle.ignition_raw bool
RAIN:X RAIN:1 vehicle.rain bool
TEMP:XX.X TEMP:23.5 vehicle.ext_temp_raw float (°C)
PARK:keys PARK:FL=45,FR=123,RL=200,RR=180 vehicle.parking_raw dict {fl, fr, rl, rr} → int (cm)

IMMO:X IMMO:1 vehicle.immo_ok bool

Debug messages (SWC:..., MUSIC:..., STALK:...) are logged but not published to the event bus. Unrecognised lines are logged at debug level.

Timing

Message Frequency

Verification

Check serial connection

# Verify Arduino is detected
ls -la /dev/ttyACM*
# Should show: /dev/ttyACM0 (Pro Micro)

ls -la /dev/ttyUSB*
# Should show: /dev/ttyUSB0 (Nano, if connected)

# Check dmesg for USB enumeration
dmesg | grep -i "ttyACM\|ttyUSB\|arduino\|ch341\|cdc_acm"

Test Pro Micro serial output

# Install minicom if not present
sudo apt install minicom

# Open serial monitor for Pro Micro
minicom -D /dev/ttyACM0 -b 115200

# Expected output on startup:
#   BCM v7 Input Controller ready (encoder + buttons + SWC + music + brightness)
# Then every 2 seconds:
#   LIGHT:512
# Press buttons to see SWC/MUSIC debug lines

Test Nano serial output

# Open serial monitor for Nano
minicom -D /dev/ttyUSB0 -b 9600

# On reset you should see:
#   {"event":"ready","fw":"bcm-domain-a-v8.5"}

# Health-check (type in minicom, end with Enter):
#   {"cmd":"ping"}
# Expected reply:
#   {"event":"pong"}

# Dump current state (learned codes, BLE MAC, RSSI threshold):
#   {"cmd":"status"}

# Set the 7" display backlight to 50% (D9 PWM duty ~2.5V average):
#   {"cmd":"backlight","display":"large","brightness":50}

Test BCM integration

# Check BCM log for Arduino serial detection
sudo journalctl -u bcm-headunit --no-pager | grep -i "arduino"
# Should show: "Arduino serial listener started: /dev/ttyACM0"

# Monitor event bus for live sensor data
# (in BCM debug console or log)
# Look for: arduino.light_level, vehicle.doors, vehicle.ignition_raw
Permissions

If /dev/ttyACM0 or /dev/ttyUSB0 returns "permission denied", add the BCM user to the dialout group: sudo usermod -aG dialout $USER then log out and back in.
