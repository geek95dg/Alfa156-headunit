Display & Touch Dual display setup, touchscreen calibration, and boot splash configuration for M910q

Overview

The Lenovo M910q has 2× mini-DisplayPort outputs, providing native dual-display support without any USB display adapters. Both outputs connect to car displays using passive DP-to-HDMI adapters. The primary display is a 7" IPS touchscreen (1024×600) for the main BCM dashboard, and the secondary is a 4.3" TFT (800×480) for the status dashboard.

This page covers the complete display pipeline: hardware connections, X11 kiosk setup (autologin, xrandr layout, Chromium instances), USB touchscreen calibration, DRM boot splash on both screens, and troubleshooting common issues.

Adapters matter

Use passive DP-to-HDMI adapters (not active converters). The M910q's Intel HD 530 supports HDMI output natively through passive adapters. Active adapters add latency and are unnecessary. Typical cost: 10–20 PLN each.

Display Hardware

Output Display Resolution Content
DP-1 → HDMI-1 7" IPS touchscreen 1024×600 BCM dashboard (port 5002)
DP-2 → HDMI-2 4.3" TFT 800×480 Status dashboard (port 5003)

Connector Naming

Two different subsystems use different names for the same physical outputs:

  • xrandr (X11): HDMI-1 and HDMI-2
  • DRM (kernel/framebuffer): HDMI-A-1 and HDMI-A-2

The setup-x86.sh script translates between these naming conventions automatically. You only need to be aware of the difference when debugging splash (DRM) vs kiosk (X11) issues.

Discover Connected Outputs

To see which DRM connectors are active: 

for f in /sys/class/drm/card*-*/status; do echo "$f: $(cat $f)"; done

Expected output with both displays connected:

/sys/class/drm/card0-HDMI-A-1/status: connected
/sys/class/drm/card0-HDMI-A-2/status: connected

Kiosk Setup

The setup-x86.sh script configures a complete kiosk environment that boots directly into dual Chromium windows without any desktop environment. Here is what the script sets up:

X11 Xwrapper

Allows non-root users to start the X server: 

# /etc/X11/Xwrapper.config
allowed_users=anybody

Autologin on tty1

A systemd getty override enables automatic login on the first virtual terminal: 

# /etc/systemd/system/getty@tty1.service.d/autologin.conf
[Service]
ExecStart=
ExecStart=-/sbin/agetty --autologin bcm --noclear %I $TERM

Login Shell → X Server

The .bash_profile for the bcm user starts X automatically on tty1, but waits for the boot splash to finish first (see Boot Splash below).

.xinitrc Pipeline

When X starts, .xinitrc performs these steps in order:

  1. Configure xrandr layout (side-by-side, main display on the left)
  2. Map the USB touchscreen to the correct display output
  3. Launch the main Chromium instance on the 7" display (port 5002)
  4. Launch the small Chromium instance on the 4.3" display (port 5003)

Chromium Policy

A managed policy file disables all browser prompts that would interfere with kiosk operation:

  • No first-run dialog or welcome page
  • No popup windows or new tabs
  • No translate bar
  • No password manager prompts
  • No crash recovery bubble

Touch Calibration

USB touchscreens appear as separate input devices in X11. By default, touch events map to the entire X screen (which spans both displays). The setup script uses xinput map-to-output to constrain touch events to the correct display.

How It Works

The setup script sets a TOUCH_DEVICE variable with the name of the detected touchscreen, then maps it: 

# In .xinitrc (generated by setup-x86.sh)
xinput map-to-output "$TOUCH_DEVICE" "$MAIN_OUTPUT"

Find Your Touch Device

DISPLAY=:0 xinput list

Look for entries containing "touch", "HID", or your display's brand name. Common touchscreen device names:

  • QDtech MPI5001: QDtech MPI5001 or HID 222a:0001
  • Waveshare: WaveShare WaveShare or wch.cn USBtiny
  • Generic USB HID: HID xxxx:xxxx (vendor:product format)

Diagnostics

The setup script logs all touch mapping actions to /tmp/bcm-xinput.log. Check this file to see what happened during the last X startup: 

cat /tmp/bcm-xinput.log

Touch Offset Fix

Touch is offset or maps to the wrong screen

If touch events land on the wrong screen or are offset, verify that MAIN_OUTPUT in .xinitrc matches the actual xrandr output name for your 7" display. Run DISPLAY=:0 xrandr and check which output shows 1024x600. The name must match exactly (e.g., HDMI-1 not HDMI1).

Boot Splash

Two systemd services provide boot splash video on both displays before X11 starts. They use mpv with --vo=drm for direct framebuffer rendering — no X server is needed.

Splash Services

Service DRM Connector Video File Resolution
bcm-splash-main HDMI-A-1 /opt/bcm/assets/splash/main.mp4 1024×600
bcm-splash-small HDMI-A-2 /opt/bcm/assets/splash/small.mp4 800×480

DRM Connector Configuration

The DRM connector names are set via systemd drop-in overrides so they can be changed per-machine without editing the main service files: 

# /etc/systemd/system/bcm-splash-main.service.d/drm.conf
[Service]
Environment="DRM_CONNECTOR=HDMI-A-1"

# /etc/systemd/system/bcm-splash-small.service.d/drm.conf
[Service]
Environment="DRM_CONNECTOR=HDMI-A-2"

DRM Wait Loop

The i915 GPU driver may take a few seconds to initialize after boot. The splash service includes a wait loop that checks for /dev/dri/card0 up to 10 seconds before giving up: 

# Wait for GPU (i915 driver load)
for i in $(seq 1 10); do
    [ -e /dev/dri/card0 ] && break
    sleep 1
done

Splash Lifecycle

  1. System boots, systemd starts bcm-splash-main and bcm-splash-small
  2. Each service waits for /dev/dri/card0 (up to 10 s)
  3. mpv plays the splash video on the DRM framebuffer
  4. Splash loops until the Flask backend responds on :5002, then exits
  5. .bash_profile waits for splash to finish before starting X
  6. X starts, xrandr takes over the displays, Chromium launches

Placeholder Videos

If no custom splash videos are provided, the setup script generates placeholder videos using ffmpeg: 

# Generated automatically by setup-x86.sh
ffmpeg -f lavfi -i color=c=black:s=1024x600:d=5 \
       -vf "drawtext=text='BCM v8.5':fontsize=48:fontcolor=white:x=(w-tw)/2:y=(h-th)/2" \
       -c:v libx264 -pix_fmt yuv420p /opt/bcm/assets/splash/main.mp4

ffmpeg -f lavfi -i color=c=black:s=800x480:d=3 \
       -vf "drawtext=text='BCM':fontsize=36:fontcolor=white:x=(w-tw)/2:y=(h-th)/2" \
       -c:v libx264 -pix_fmt yuv420p /opt/bcm/assets/splash/small.mp4

Custom Splash

To use your own splash videos, copy them to:

  • /opt/bcm/assets/splash/main.mp4 — 1024×600, H.264, ~8 s recommended (audio optional)
  • /opt/bcm/assets/splash/small.mp4 — 800×480, H.264, ~5 s recommended (silent)
Splash encoding tips

Use H.264 Baseline profile for fastest decode on the Intel HD 530. Keep file size under 5 MB for instant playback from NVMe. If the main splash includes audio, the mpv DRM output will route it through the default PipeWire/ALSA sink (typically the USB DAC if configured).

Chromium Kiosk

Two separate Chromium instances run in --app= mode (no address bar, no tabs, no browser UI). Each instance targets a different Flask dashboard on a different display.

Instance Configuration

Instance URL Window Position User Data Dir
Main (7") http://localhost:5002 --window-position=0,0 /tmp/bcm-chromium-main
Small (4.3") http://localhost:5003 --window-position=1024,0 (offset by main width) /tmp/bcm-chromium-small

Key Chromium Flags

chromium --app=http://localhost:5002 \
         --window-position=0,0 \
         --window-size=1024,600 \
         --user-data-dir=/tmp/bcm-chromium-main \
         --no-first-run \
         --disable-infobars \
         --disable-session-crashed-bubble \
         --noerrdialogs \
         --kiosk

Clean on Boot

User data directories are located in /tmp/bcm-chromium-*, which is a tmpfs mount. This means Chromium starts with a clean profile on every boot — no stale cache, no session restore prompts, and no disk wear on the NVMe SSD.

Policy File

A managed policy file is installed to suppress all browser prompts: 

# /etc/chromium/policies/managed/bcm-kiosk.json
{
  "AutofillAddressEnabled": false,
  "AutofillCreditCardEnabled": false,
  "BrowserSignin": 0,
  "DefaultPopupsSetting": 2,
  "PasswordManagerEnabled": false,
  "TranslateEnabled": false,
  "BookmarkBarEnabled": false
}

Troubleshooting

Displays Are Merged (Mirrored)

If both displays show the same content instead of side-by-side layout:

  • Check .xinitrc for the xrandr --output HDMI-2 --right-of HDMI-1 command
  • Run DISPLAY=:0 xrandr and verify both outputs are listed separately
  • If xrandr shows only one output, check the DP-to-HDMI adapters — one may be faulty or not fully seated
  • Some cheap adapters do not support EDID passthrough; try a different adapter

Touch Events on Wrong Screen

  • Check /tmp/bcm-xinput.log for the map-to-output command
  • Verify TOUCH_DEVICE matches the actual device name in xinput list
  • Verify MAIN_OUTPUT matches the xrandr name for the 7" display
  • If displays were swapped physically, swap the DP adapter cables or update MAIN_OUTPUT

Splash Not Playing

Symptom Cause Fix
Black screen, no splash DRM device not ready — /dev/dri/card0 missing Check lsmod | grep i915; if missing, the GPU driver did not load. Verify BIOS has integrated graphics enabled.
Splash on wrong screen DRM connector name mismatch Check for f in /sys/class/drm/card*-*/status; do echo "$f: $(cat $f)"; done and update the systemd drop-in override to match
Splash plays but never stops Flask not starting on port 5002 Check sudo journalctl -u bcm-headunit for Flask errors; splash waits for curl localhost:5002 to succeed
mpv error: "no DRM connector" Connector name uses X11 format instead of DRM format Use HDMI-A-1 (DRM) not HDMI-1 (X11) in the splash service

X Starts Before Splash Finishes

  • The .bash_profile should contain a wait loop that checks if the splash service is still active
  • Verify with: systemctl is-active bcm-splash-main
  • If the splash service exits immediately (failed), X will start right away — check splash logs for errors
  • Ensure the splash service is Type=simple (not oneshot) so is-active reports correctly while mpv is running
