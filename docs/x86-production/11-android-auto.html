Android Auto OpenAuto compilation, wired & wireless AA setup, and x86 display pipeline

Overview

OpenAuto (built on openauto + aasdk from the openDsh project) provides both wired and wireless Android Auto for BCM. On the x86 platform, AA renders to an Xvfb virtual display and streams to the browser-based dashboard via MJPEG. Touch input is forwarded from the browser back to the virtual display using xdotool.

This page covers compiling OpenAuto from source, setting up wired and wireless Android Auto, and the internal display pipeline that connects the Qt-based OpenAuto renderer to the BCM web dashboard.

AA is optional

Android Auto is an optional feature. All other BCM functions (dashboard, OBD-II, cameras, audio, sensors) work without it. Complete all other build stages (sections 1–10) before attempting this step.

Build Dependencies

Install all required build tools, Qt5 libraries, GStreamer plugins, and the Xvfb virtual framebuffer. This is a one-time operation — these packages remain installed for future rebuilds. 

sudo apt install -y \
    cmake build-essential \
    libboost-all-dev libusb-1.0-0-dev libssl-dev \
    libprotobuf-dev protobuf-compiler \
    qtbase5-dev qtchooser qt5-qmake qtbase5-dev-tools \
    qtmultimedia5-dev libqt5multimedia5-plugins \
    qtconnectivity5-dev qtdeclarative5-dev \
    qml-module-qtquick2 qml-module-qtquick-controls2 \
    libqt5websockets5-dev libqt5bluetooth5 \
    libgstreamer1.0-dev libgstreamer-plugins-base1.0-dev \
    gstreamer1.0-plugins-base gstreamer1.0-plugins-good \
    gstreamer1.0-plugins-bad gstreamer1.0-plugins-ugly \
    gstreamer1.0-libav \
    libtag1-dev librtaudio-dev \
    xvfb matchbox-window-manager
Qt5 vs Qt6

OpenAuto requires Qt5. Debian 13 ships both Qt5 and Qt6; make sure the qt5-qmake and qtbase5-dev packages are installed, not their Qt6 equivalents. The qtchooser package handles version selection.

Build aasdk

The aasdk library implements the Android Auto protocol (USB and TCP transport, protobuf messaging, SSL handshake). It must be built first since openauto depends on it. 

cd /tmp
git clone --recurse-submodules https://github.com/openDsh/aasdk.git
cd aasdk

# Fix: OpenSSL 3.0 removed FIPS_mode_set
sed -i 's/FIPS_mode_set(0);/\/\/ FIPS_mode_set(0); \/\/ removed in OpenSSL 3.0/' \
    src/Transport/SSLWrapper.cpp

mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
make -j$(nproc)
sudo make install
sudo ldconfig
OpenSSL 3.0 FIPS fix

The upstream aasdk calls FIPS_mode_set(0) which was removed in OpenSSL 3.0 (shipped with Debian 12+). The sed command comments out this call. Without this fix, the build will fail with undefined reference to FIPS_mode_set.

Build h264bitstream

The h264bitstream library parses H.264 NAL units. The upstream repository has no Makefile, so we compile and install it manually. 

cd /tmp
git clone https://github.com/aizvorski/h264bitstream.git
cd h264bitstream

gcc -c -fPIC h264_stream.c h264_sei.c -I.
ar rcs libh264bitstream.a h264_stream.o h264_sei.o

sudo cp libh264bitstream.a /usr/local/lib/
sudo cp h264_stream.h h264_sei.h h264_avcc.h h264_slice_data.h bs.h \
    /usr/local/include/
sudo ldconfig

This creates a static library (libh264bitstream.a) and installs the headers to /usr/local/include/. The openauto build will find them via the default search paths.

Build openauto

The openauto project contains the main autoapp binary that renders the Android Auto projection. 

cd /tmp
git clone --recurse-submodules https://github.com/openDsh/openauto.git
cd openauto

# Fix: Debian 13 librtaudio 6.x renamed RtAudioError
sed -i 's/catch(const RtAudioError& e)/catch(const std::exception\& e)/g' \
    openauto/Projection/RtAudioOutput.cpp

mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
make -j$(nproc)
sudo make install
RtAudio fix for Debian 13

Debian 13 (Trixie) ships librtaudio 6.x which renamed the RtAudioError exception class. The sed command replaces it with the standard std::exception catch. Without this fix, the build fails with RtAudioError was not declared.

Verify Installation

After a successful build, the autoapp binary should be installed at /usr/local/bin/autoapp. 

ls -la /usr/local/bin/autoapp
# Should show the binary (~5MB)

Restart BCM so it detects the newly installed OpenAuto binary:

sudo systemctl restart bcm-ignition-watcher
sudo journalctl -u bcm-headunit --no-pager | grep -i openauto
# Should show: "OpenAuto found: /usr/local/bin/autoapp"

BCM searches for the autoapp binary in three locations at startup: /usr/local/bin/autoapp, /opt/openauto/bin/autoapp, and /usr/bin/autoapp. The first one found is used.

Wired Android Auto

Wired Android Auto uses a direct USB connection between the phone and the M910q. This is the simplest setup and provides the lowest latency.

Setup Steps

  1. Install Android Auto from the Google Play Store on your phone
  2. Enable Developer options on the phone (Settings → About phone → tap Build number 7 times)
  3. Enable USB debugging in Developer options
  4. Connect the phone to the M910q via a USB cable (use one of the USB 3.0 ports)
  5. Accept the "Allow USB debugging" prompt on the phone
  6. Select "Android Auto" mode when prompted
  7. AA appears on BCM screen A2 (the multimedia page in the dashboard)
USB cable quality matters

Use a high-quality USB cable that supports data transfer (not a charge-only cable). USB 3.0 cables provide better throughput for the H.264 video stream. If the phone is not detected, try a different cable first.

Wireless Android Auto

Wireless Android Auto uses Bluetooth for initial pairing and the 5 GHz WiFi access point for the actual data stream. This requires the Fenvi FU-AX1800 (or compatible WiFi 6 card) and a working hostapd setup from section 10.

Prerequisites

  • WiFi AP running: ALFA_AA on 5 GHz band (configured via hostapd)
  • Bluetooth pairing completed and phone trusted
  • autoapp binary installed (see sections above)

Connection Flow

  1. Phone pairs with BCM via Bluetooth
  2. Phone discovers the ALFA_AA WiFi access point through the BT connection
  3. Phone connects to the AP and receives a DHCP address (192.168.44.x range)
  4. AA video/audio stream flows over the WiFi connection

BCM Configuration

The WiFi credentials must be set in bcm_config.yaml so that BCM knows which AP to advertise during the BT pairing handshake: 

# config/bcm_config.yaml:
wifi:
  enabled: true
  ssid: ALFA_AA
  password: AlfaRomeo156
5 GHz is required for wireless AA

Android Auto requires a 5 GHz WiFi connection for wireless mode. The 2.4 GHz band does not have enough bandwidth for the H.264 video stream. If using the stock Intel 8265 card, verify it can create a 5 GHz AP — some firmware versions restrict AP mode to 2.4 GHz. The Fenvi FU-AX1800 (Intel AX200) is the recommended upgrade if 5 GHz AP is unstable.

How AA Display Works on x86

On the x86 platform, BCM runs a browser-based dashboard (Flask + Chromium). OpenAuto is a Qt application that renders to a native X11 window. To bridge these two worlds, BCM uses a virtual framebuffer pipeline:

Display Pipeline

Stage Component Description
1 Xvfb Virtual framebuffer running at display :99 — no physical monitor needed
2 OpenAuto (autoapp) Renders AA projection via Qt xcb platform plugin to display :99
3 ffmpeg Captures display :99 and encodes as MJPEG stream
4 BCM Flask Serves the MJPEG stream at /aa/stream endpoint
5 Browser Displays the MJPEG stream in an <img> tag inside the AA page

Touch Input Pipeline

Touch input flows in the reverse direction — from the browser back to the virtual display:

  1. User taps on the AA area in the browser (Chromium on the physical touchscreen)
  2. Browser sends a POST /aa/touch request with {x, y} coordinates
  3. BCM translates the coordinates to the Xvfb virtual display space
  4. xdotool mousemove --screen 0 <x> <y> click 1 is executed on display :99
  5. OpenAuto receives the click event and forwards it to the phone via the AA protocol

Canvas Sizing

The AA canvas size is calculated dynamically based on the dashboard dimensions. BCM reserves a 48 px AppBar at the top and a 48 px NavBar at the bottom: 

# From src/multimedia/openauto.py:
# Canvas = (dashboard_width, dashboard_height - appbar - navbar)
# Default: (1024, 600 - 48 - 48) = 1024 x 504

dash_w = config.get("display.dashboard.width", 1024)
dash_h = config.get("display.dashboard.height", 600)
appbar = config.get("display.appbar_px", 48)
navbar = config.get("display.navbar_px", 48)
canvas = (dash_w, max(240, dash_h - appbar - navbar))

If display.multimedia.width and display.multimedia.height are explicitly set in bcm_config.yaml, those values override the automatic calculation.

Why Xvfb?

On ARM (OPi 5 Pro), OpenAuto renders directly to a physical HDMI output using EGL/SDL2. On x86, the physical displays are already used by Chromium kiosk instances. Xvfb provides a virtual display that OpenAuto can render to without conflicting with the existing X11 session. The MJPEG streaming approach adds ~30 ms latency but keeps the architecture clean and avoids compositing issues.

Troubleshooting

autoapp not found

Symptom Cause Fix
BCM log: "OpenAuto not found" Binary not in expected path Check ls /usr/local/bin/autoapp — if missing, re-run sudo make install in the openauto build directory
autoapp: error while loading shared libraries aasdk libraries not in linker cache Run sudo ldconfig and verify ls /usr/local/lib/libaasdk*

Phone Not Detected (Wired)

Symptom Cause Fix
Phone charges but no AA prompt USB debugging not enabled or charge-only cable Enable USB debugging in Developer options; try a data-capable USB cable
lsusb does not show phone Bad USB port or cable Try a different USB 3.0 port on the M910q; test the cable with another device
Phone shows "Allow USB debugging" but AA never starts Android Auto app not installed or outdated Install/update Android Auto from Play Store; reboot phone

Wireless AA Timeout

Symptom Cause Fix
Phone pairs via BT but never connects to WiFi 5 GHz AP not running or phone cannot see it Verify systemctl status hostapd; check iw dev for AP on 5 GHz channel
Phone connects to WiFi but AA does not start DHCP not assigning address Check journalctl -u dnsmasq for lease assignment; verify 192.168.44.0/24 subnet
AA connects then disconnects after a few seconds WiFi signal too weak (2.4 GHz fallback) Confirm AP is on 5 GHz: iw dev | grep channel; consider upgrading to Fenvi AX200
Wireless AA lag or stutter WiFi interference or low signal Move antenna position; switch to a less congested 5 GHz channel in /etc/hostapd/hostapd.conf

Touch Not Reaching AA

Symptom Cause Fix
AA video shows but taps do nothing xdotool not installed or DISPLAY not set Install: sudo apt install xdotool; verify DISPLAY=:99 is set in the touch handler
Taps land in wrong position Canvas size mismatch between browser and Xvfb Check display.multimedia.width/height in config matches Xvfb resolution
Touch works but with noticeable delay Normal for MJPEG pipeline (~30–50 ms) This is expected; reduce MJPEG quality or increase frame rate if needed
